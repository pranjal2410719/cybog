## 2. Report Generation & Distribution

### 2.1 Format Decision
- **Primary**: HTML reports – human‑readable, embedded in the platform UI, supports rich tables, charts, and navigation.
- **Secondary**: PDF reports – for offline sharing, executive summaries, and archival.
- Both formats will be generated by the existing `HTMLReporter` and `JSONReporter` classes; a new `PDFReporter` wrapper will be added for PDF export.

### 2.2 Integration into CI/CD
- Add a new step in the CI pipeline (e.g., `ci/github/workflows/ci.yml`) that runs after successful test execution.
- Steps:
  1. Generate HTML report for the latest assessment run.
  2. Generate PDF report (optional, for stakeholders).
  3. Upload reports to a secure artifact store (encrypted S3 bucket or internal Nexus/Artifactory).
  4. Publish a notification (Slack/email) with a link to the report.
- The CI job should fail if report generation or storage fails.

### 2.3 Secure Storage
- Reports will be stored in `s3://cybog-reports/` (or equivalent) with:
  - Server‑side encryption (AES‑256).
  - Role‑based access control (RBAC): analysts can view their own reports; managers can view all.
  - Lifecycle policy: retain for 90 days, then purge.
- The CI job will include a step to validate the existence and integrity (SHA‑256) of the uploaded artifacts.

### 2.4 Acceptance Criteria
- [ ] HTML and PDF reports are produced successfully for every assessment run.
- [ ] Reports are stored securely with proper access controls.
- [ ] CI pipeline fails fast if report generation or storage fails.
- [ ] Distributed links are accessible within the platform UI.

## 3. End‑to‑End Scan Infrastructure

### 3.1 Approved Scanning Targets
| Category | Tools | Trigger | Notes |
|----------|-------|---------|--------|
| Vulnerability Scanning | `nuclei`, `trivy`, `bandit` | On new target ingestion | Standard baseline |
| Fuzzing | `afl++`, `libFuzzer` | Periodic (daily) | Focus on parser/handler modules |
| Static Analysis | `pylint`, `bandit`, `mypy` | On code change | Enforced in CI |
| Configuration Auditing | Custom schema validators | On manifest update | Detect misconfigurations |
| Runtime Behavior | `cybog_integration.py` | Continuous | End‑to‑end pipeline simulation |

### 3.2 Automated E2E Scans
- **Scope**: Full pipeline execution from target discovery → assessment → report generation.
- **Implementation**:
  1. Create a dedicated CI job `ci/e2e-scan.yml` that:
     - Spins up a fresh `JobScheduler` instance.
     - Injects a controlled set of test targets (e.g., `test-target-001`).
     - Runs the complete pipeline and captures logs.
     - Generates both HTML and PDF reports.
  2. Introduce a “scan health” gate: the E2E job must produce at least one report with no critical failures before merging.
- **Traceability Framework**:
  - Assign a unique `scan-id` to each E2E run.
  - Link the scan ID to the corresponding assessment ID in `AssessmentState`.
  - Store correlation metadata (start/end time, duration, resource usage) in `cybog/cybog/state/scan_trace.json`.
  - Visualize traceability in the platform dashboard (scan timeline, bottleneck identification).

### 3.3 Acceptance Criteria
- [ ] E2E scan job runs successfully and produces reports for test targets.
- [ ] Traceability records are created and linked to assessment records.
- [ ] Critical scan failures trigger an alert (see Section 4).

## 4. Quality Assurance & Monitoring

### 4.1 Performance Benchmarks
- **Metrics**:
  - Pipeline end‑to‑end latency (target ≤ 15 min for a typical assessment run).
  - Throughput: ≥ 50 assessments/minute on the staging cluster.
  - Memory/CPU utilization per node (keep under 80% average).
- **Measurement**:
  - Instrument the `JobScheduler` with timing hooks.
  - Export benchmark data to `cybog/metrics/benchmark.json`.
  - Compare against baseline (Phase 1) to detect regressions.

### 4.2 Alerting Rules
| Condition | Channel | Severity | Action |
|-----------|---------|----------|---------|
| Pipeline failure (non‑critical) | Slack #cybog-alerts | Warning | Log + Slack notification |
| Pipeline failure (critical) | PagerDuty + Slack | P1 | Page on‑call engineer + ticket creation |
| Report generation timeout (> 5 min) | Email + Slack | Warning | Notify team + retry attempt |
| Resource exhaustion (CPU > 85%) | Prometheus alert | Critical | Scale nodes / pause non‑critical jobs |
| New vulnerability pattern detected | Slack #cybog-security | High | Immediate investigation |

### 4.3 Audit Trail Enhancement
- Extend `AssessmentState` to record:
  - `scan_id` (E2E scan identifier)
  - `report_version` (JSON/HTML report hash)
  - `quality_checks_passed` (list of passed benchmarks)
  - `last_modified` timestamp with user ID
- Store immutable audit logs in `s3://cybog-audit/` with WORM (Write‑Once‑Read‑Many) protection.
- Enable compliance reporting (GDPR, SOC 2) by exposing these logs via the admin portal.

### 4.4 Acceptance Criteria
- [ ] Performance benchmarks meet or exceed Phase 1 baselines.
- [ ] All alerting rules are deployed and firing correctly in a test environment.
- [ ] Audit trails are captured for every assessment and report generation.
- [ ] Dashboard displays real‑time QA metrics (latency, throughput, error rates).
